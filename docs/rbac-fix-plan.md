## 二、P0 — bug 级速修

### 0.1 `_read_roles()` 静默返回空骨架

- **现状**：`server/roles_admin_api.py:49-57`——文件损坏（JSON 解析失败等）时与
  「文件不存在」同样静默返回默认骨架 `{"admin": {"role": "admin"}}`，管理页表现为
  「看起来没有其他用户」，属数据事故级误导。
- **改法**：`FileNotFoundError` 保留默认骨架（首次部署合法路径）；**其他异常改为抛
  `HTTPException(500)`**，detail 带 `roles.json` 路径与具体错误原因。

> ✍️ 通俗解读：如果 `roles.json` 配置文件写坏了，现在系统不报错，页面假装只剩管理员账号，
> 让人误以为其他用户全部丢失。
> 修改：刚部署文件还不存在，允许用默认配置；文件损坏则直接报 500 错误，写明哪个文件出错。

### 0.2 `POST /roles` 无并发保护

- **现状**：`roles_admin_api.py:108-129`——全量覆写式保存，两个管理员页同时编辑时
  后保存者整体覆盖先保存者的改动（丢更新）。
- **改法**：保存路径加文件锁 `roles.json.lock`（`O_CREAT|O_EXCL` + 超时重试 +
  崩溃残留锁的过期兜底）；锁内完成「读 existing → 哈希化 → 写 tmp → `os.replace`」。

> ✍️ 通俗解读：两个管理员同时编辑用户列表并保存，后点保存的会覆盖前面人的修改，造成数据丢失。
> 修改：加文件锁，同一时间只允许一个人执行保存操作。

### 0.3 前端删除行仅改本地状态，无未保存提示

- **现状**：`team/index.tsx` 删行只是从本地数组移除，不点「保存」不生效，
  界面却已看不到该用户，误以为已删除。
- **改法**：维护 dirty 状态——有未保存变更时顶栏显示「N 项未保存」；
  离开页面/刷新时拦截提示。

> ✍️ 通俗解读：页面上点删除用户，界面立刻隐藏该用户，但不点保存后台不会真正删除，
> 容易让人误以为已经删完。
> 修改：页面标记未保存变更，切页面或者刷新的时候弹窗提醒。

## 三、P1 — admin 判定统一 + 用户名校验

### 3.1 admin 判定统一为 roles.json 的 role 字段（评审问题 3）

- **现状**：两套标准——后端 `roles_admin_api.py:44-46` 硬编码 `user_id != "admin"`；
  前端 `team/index.tsx:225`、`AppSidebar.tsx` 硬编码 `getUserId() === 'admin'`。
  建第二个 admin 账号后，管理页进得去（前端只认名字）但 API 全 403。
- **改法**：
  1. `auth.py` 提供共享的 `get_user_role(user_id)`（读 roles.json，复用
     `role_access_policy` 的 5 秒缓存逻辑）；
  2. `_roles_require_admin` 改为 `get_user_role(user_id) == "admin"`；
  3. 新增轻量 `GET /me`（返回 `{user_id, role}`，任何登录用户可调）；
  4. 前端两处入口判断改按 `/me` 返回的 role 显示。

> ✍️ 通俗解读：现在前端、后端两套不一样的逻辑判断谁是管理员。新建第二个管理员账号，
> 页面能打开管理后台，但调用接口全部报权限错误。
> 修改：统一读取 `roles.json` 判断角色；新增 `/me` 接口返回当前登录人的身份角色；
> 前端全部使用这个接口结果做判断。

### 3.2 用户名白名单校验，堵文件隔离穿透（评审问题 4）

- **现状**：`POST /roles` 不校验用户名。磁盘隔离依赖
  `server/per_user_workspace.py:36-43` 的 `safe_user_component` 净化
  （`[^A-Za-z0-9_-]`→`_` + 截断 64），两个不同用户名净化后可碰撞同一目录
  （如 `a/b` 与 `a:b` 都变 `a_b`），导致工作区/记忆互相可见可写。
  `scripts/common.py:148-153` 还有一份相同镜像。
- **改法**：
  1. 后端：`POST /roles` 保存入口校验用户名 `^[A-Za-z0-9_-]{1,64}$`
     （与净化规则对齐，保证「净化前即合法、净化无碰撞」），不合法返回 422
     并点名哪个用户名；`admin` 键自身豁免；
  2. 前端：`team/index.tsx` 新增行输入时同规则即时校验 + 红字提示；
  3. `common.py` 镜像保留，注释改为「入口已校验，此处仅为防御」。

> ✍️ 通俗解读：用户名可以输入冒号、斜杠这类特殊符号，系统会把特殊符号替换成下划线。
> 两个不一样的用户名处理完变成同一个文件夹，造成两个用户数据互相窜。
> 修改：用户名只允许字母数字下划线横杠；前端输入立刻提示，后端再次拦截；
> 旧的兼容代码保留仅作为兜底防护。

## 四、P2 — 脚本层用户表收敛到 roles.json（评审问题 1，核心）

### 4.0 前置认知：为什么必须动后端

密码哈希化后（`auth.py` PBKDF2），**包括 admin 在内任何人都拿不到用户明文密码**。
而以下脚本场景依赖「以每个用户身份调 API」：

- `scripts/validate_setup.py:40` 可见性矩阵（逐用户 `GET /agent/`）；
- `scripts/configure_embedding.py:59` 给每个用户发 local_bge 凭据；
- `scripts/chat_smoke.py` 多用户冒烟。

所以「脚本拿明文」这条路在哈希化后天然断了——**只改 `common.py` 的读取来源救不活这些场景**，
需要后端配套支持代操作。

> ✍️ 通俗解读：现在密码只存哈希值（不可逆的散列），任何人都拿不到原始明文密码。
> 但是自动化脚本需要模拟各个普通用户调用接口；旧方案靠读取配置里面明文密码，已经不能用，
> 后端要增加「管理员代替其他用户操作」能力。

### 4.1 后端支持代操作（取舍点 ①，推荐方案）

- **改法**：请求头 `X-On-Behalf-Of: <user>`——仅当真实身份 `role == "admin"`
  且 `admin_edit: true` 时生效；框架身份层仍视为 admin（鉴权通过），
  资源归属记为被代用户。与现有 `admin_edit` 语义一致。
- **涉及**：`auth.py`（`get_current_user_id` 适配）+ `role_access_policy.py`
  （可见性按被代用户算）。
- **备选**（已否决）：脚本双写 `.env` 明文——破坏单一事实源，正是本次要消灭的东西。

> ✍️ 通俗解读：新增特殊 HTTP 请求头 `X-On-Behalf-Of`。管理员带上这个头，就可以代替别的用户
> 执行接口，不需要知道别人密码。注意：仅限具备 `admin_edit` 权限的管理员生效，
> 普通用户带了也没用。不采用继续把明文密码写配置文件的方案，会造成两份用户数据，隐患大。

### 4.2 `scripts/common.py` 重写认证与用户清单

| 函数 | 现状 | 改为 |
|------|------|------|
| `agents_users()`（L58-60） | 读 `.env` 的 `AGENTS_USERS` | 读 `roles.json` 的 `users` 键（仅用户清单，不含密码） |
| `auth_headers()`（L94-110） | 用 `.env` 明文构造 Basic 头 | admin Basic 认证：密码取环境变量 `AGENTSCOPE_PASSWORD`，缺失时 `getpass` 交互输入；需要以某用户身份时额外带 `X-On-Behalf-Of` 头 |

> ✍️ 通俗解读：脚本不再读取旧配置 `.env` 获取用户列表和密码；从 `roles.json` 读取用户名单；
> 脚本以管理员账号登录（密码从环境变量 `AGENTSCOPE_PASSWORD` 取，没有就手动输入），
> 通过上面的代操作请求头模拟普通用户。

### 4.3 调用方适配（4-5 个脚本）

`configure_model.py:121`、`configure_embedding.py:59`、`validate_setup.py:40`、
`chat_smoke.py`、`_auth_probe.py`——改走新认证；`validate_setup.py` 可见性矩阵
改为 admin + `X-On-Behalf-Of` 逐用户枚举（不再需要明文密码，矩阵保留）。

> ✍️ 通俗解读：修改全部相关自动化脚本，全部切换到这套新的认证逻辑。

### 4.4 清理旧引用

- `scripts/common.py:156-173` `parse_share_rules` 删除（唯一外部调用方
  `migrate_env_share_to_roles.py` 改为自带解析）；
- `validate_setup.py:6-8`、`register_agents.py:2-10` 文档字符串中
  `AGENTS_OWNER` / `AGENTS_DEFAULT_SHARE` / `AGENTS_AGENT_SHARE` 旧表述更新为
  roles.json 模型描述。

> ✍️ 通俗解读：删掉已经废弃的函数；脚本注释文档把旧配置相关描述全部改成新 `roles.json` 的说明。

## 五、P3 — 删除用户生命周期（评审问题 2，核心）

### 5.1 保存时 diff + 资源清点

- **现状**：`roles_admin_api.py:108-129` 全量覆写；`role_access_policy.py:120-123`
  admin 分支只枚举 roles.json **在册** owner → 被删用户名下的 Redis 资源变成
  「幻影资源」：所有人不可见、管理页清不掉、只能直连 Redis。
- **改法**：`POST /roles` 保存时计算 `removed = existing_users - payload_users`，
  逐个清点其名下 agent / KB / 凭证数量。

> ✍️ 通俗解读：现在直接删掉一个用户，该用户创建过的助手、知识库、密钥还残留在 Redis
> 数据库里面（那是正式数据，不是缓存），谁都看不到，页面删不掉，只能手动操作数据库
> （叫幻影资源）。
> 修改：删除用户的时候，先统计这个用户名下全部的资源。

### 5.2 处置决策流（取舍点 ②，推荐方案）

- 名下**无**资源 → 正常保存；
- 名下**有**资源 → 不直接保存，返回 **409 + 资源清单**，前端弹对话框让 admin
  三选一：
  1. **转移给 admin**（推荐默认）——转移后自动落入「归属即规则」：agent 按
     `user_agents` 白名单可见、KB/凭证变全员只读，模型零新增概念；
  2. 连带删除资源（不可逆，需二次确认）；
  3. 取消本次保存。
- **涉及**：`roles_admin_api.py` + `team/index.tsx` 决策对话框。

> ✍️ 通俗解读：如果被删用户还有资源，不让直接完成删除，弹窗给管理员 3 个选项：
> ① 全部资源转给管理员（推荐）；② 连同资源一起彻底删除（不可恢复）；③ 放弃删除操作。

### 5.3 磁盘工作区归档

磁盘 `workspaces/<agent>/users/<user>/`（记忆、会话产物、技能）**不自动删**：

- 保存成功响应带回该用户的磁盘路径清单，前端提示「请管理员手动归档」；
- 新增 `scripts/archive_user_workspace.py`：把目录改名为 `<user>.deleted-<时间戳>`
  （只改名不删除，可人工恢复）。

> ✍️ 通俗解读：硬盘上保存的聊天记忆文件程序不会自动删除；页面提示管理员路径；
> 提供脚本把文件夹重命名打上删除标记，可以后续恢复。

### 5.4 存量幻影资源一次性清理

新增 `scripts/reclaim_orphan_resources.py`：扫描 Redis 中 owner 不在 roles.json
的存量资源，列出清单确认后批量转移给 admin（修历史欠账，跑一次即可）。

> ✍️ 通俗解读：写一次性脚本，扫描历史遗留的孤儿资源，批量转给管理员，修复老数据问题。

### 5.5 用户改名（rename）——批次 P3.5（2026-10-10 新发现）

**问题**：用户名是 `roles.json` 的 `users` 键名、Redis 资源 owner、磁盘目录名
`workspaces/<agent>/users/<user>/` 三处共同的主键。前端管理页
（`web_ui/frontend/src/pages/team/index.tsx`）用户名列为纯文本展示，
行操作列只有删除按钮，**全链路没有改名能力**——打错字只能「删了重建」，
而删除会触发 5.2 的 409 资源决策流，等于改名这条路实际走不通。

**为什么不复用 `POST /roles` 全量保存**：payload 里「去掉旧键 + 加新键」与
「删除旧用户 + 新建空用户」在服务端无法区分，会误触发删除决策流（409），
也无法自动迁移资源——必须独立接口。

**API**：新增 `POST /roles/users/rename`，body `{"from": "...", "to": "..."}`：

- 校验：`from` 存在、`to` 不存在、`to` 过 3.2 的共享白名单 `^[A-Za-z0-9_-]{1,64}$`
  （校验函数提为共享 `validate_username`，与 `POST /roles` 共用）；
  `from`/`to` 均不得为 `admin`（超级管理员账号名固定）；
- 执行顺序（无跨存储事务，按「失败可幂等重试」排序）：
  1. **先迁 Redis owner**——该用户名下 agent / KB / 凭证的 owner 字段批量改；
     幂等：已为新名则跳过，可安全重试；
  2. **再改 roles.json**——`users.<old>` → `users.<new>`（密码哈希原值随迁），
     `user_agents.<old>` → `user_agents.<new>`；此步是**生效点**：
     成功后新名立即可登录、旧名立即失效；
  3. **最后磁盘目录改名**——`workspaces/<agent>/users/<old>/` → `<new>/`，
     同盘 `os.rename` 原子；失败不影响身份切换，响应中列明待重试项，
     可用 5.3 的归档脚本人工兜底；
  - 顺序论证：若先改 roles.json 后迁 Redis，失败窗口内资源 owner 是旧名
    而旧名已不在册 → 立刻变成 5.1 的幻影资源；先迁 Redis 则窗口内最多是
    「新名资源暂不可见」，不产生幻影；
- 全程置于 0.2 的文件锁保护内；响应返回各步骤结果清单
  （迁移的资源数、磁盘是否改名成功）。

**前端**（`team/index.tsx`）：用户名旁加铅笔按钮 → 小对话框输入新名
（前端即时白名单校验，复用 3.2 的正则）→ 调 rename → 成功后本地更新该行
键名并 toast 各步骤结果。**不引入整行编辑弹窗**（本期范围已确认只做 rename，
其余字段维持现有行内直编）。

> ✍️ 通俗解读：用户名在系统里出现在三个地方：配置文件、资源库（Redis）、硬盘文件夹。
> 改名必须三处一起改，少改一处就会出现「人改了名、资源还挂在旧名下」的孤儿数据。
> 所以做成专门接口，按「先迁资源、再改配置、最后改文件夹」的顺序执行——
> 中途断了可以重跑，不会产生谁也看不到的孤儿资源。管理员账号 admin 不允许改名。

## 八、评审反馈追加（2026-10-10）：user 主键引入不可变 id（决策 ③ 细化）

> 来源：对本文档的二次评审。结论先行：**在迁库设计冻结前把 roles.json 的 user 主键从用户名换成不可变 id**。核心论据不是「更规范」，而是三笔账：rename 自伤、迁库返工、迁移机器已在手。

### 8.1 为什么是现在

1. **P3.5 rename 是自然键自伤的补丁**：用户名同时充当登录凭据、Redis owner、磁盘目录名、roles.json 主键，改名才需要三存储级联迁移。引入 id 后 rename 退化为「改一个字段」，已实现的三存储迁移逻辑（`_rename_workspace_dirs` / Redis owner 批量改写）**不浪费——原样转为一次性 id 迁移脚本的内核**；
2. **迁库轮的账**：users 表建主键时，若主键是用户名，改名 = 级联更新所有外键（同样的级联问题在库里重演）；若主键是 id，roles.json 里的 id 直接平移为表主键，**零二次换键**。现在不加，迁库时补做「用户名→id」全量迁移，同样的活干两遍；
3. **问题 D 收口一半**：磁盘目录改用 id（生成时即保证 `[A-Za-z0-9_-]`），净化碰撞对目录层不再存在；3.2 的用户名白名单降级为「登录名可用性约束」。

### 8.2 schema 草案（roles.json）

```json
{
  "admin_edit": true,
  "users": {
    "admin":        { "role": "admin", "password": "sha256$..." },
    "u_7f3k9xQ2ab": { "name": "zhangsan", "role": "member", "team": "1", "password": "sha256$..." }
  },
  "user_agents": { "u_7f3k9xQ2ab": ["<agent_id>"] }
}
```

- **id 格式**：base58 风格短随机串 10-12 位（不必 UUID——目录名可读性、长度、字符集三者兼得）；**admin 的 id 固定为字面量 `"admin"`**（保持引导约定与 `/team` 超管语义）；
- **最小字段集**：`id + name（登录名，走 3.2 白名单）+ role + password + team`；`display_name` 留给 UI 需求驱动，本轮不做；
- **roles.json 的 id 即未来库表主键**——这是本轮加 id 的核心意义，迁库时禁止二次换键。

### 8.3 认证链改动（与已落地的「换身」口径同构）

- `auth.py` `load_users()` 建 `name → (id, password_hash)` 索引；`basic_auth_user` 按登录名校验、**返回 id**——框架把 user_id 当不透明字符串，归属/可见性/工作区（`per_user_workspace`）全部自动跟随 id，`role_access_policy.py` 与 `per_user_workspace.py` 零改动；
- `get_user_role(user_id)` / `/me` / `X-On-Behalf-Of`（脚本代操作）一律以 id 为准；`/me` 增加返回 `name` 供前端展示；
- 3.2 白名单的适用对象从「roles.json 键名」收窄为「登录名 name 字段」；磁盘净化（`safe_user_component`）退为纯防御层。

### 8.4 一次性迁移脚本（复用 rename 机器，顺序沿用 5.5 的论证）

1. **先迁 Redis**——owner/user 键批量改写为 id。**清点范围必须对齐存储层全量记录类型**（`agentscope/app/storage/_base.py`）：credentials(:49)、mcps(:116)、skills(:204)、agents(:303)、**sessions(:366/452)**、**schedules(:538)**、**channels(:620)**、messages(:735，随 session)、teams(:806)，以及 KB documents（KB 键下）。⚠️ 当前已落地代码只覆盖 agents/KBs/credentials（`roles_admin_api.py:242-244, 332-357`）——**这是独立于 id 决策也必须补的缺口**：5.1 清点、5.2 转移、5.4 reclaim、5.5 rename 四处同缺 session/schedule/channel/mcp/skill/team，被删/改名用户的聊天记录、定时任务、渠道绑定现状都会丢；
2. **再改 roles.json**——键重构为 id 主键（此步是生效点：成功后按 id 认证，旧名即失效）；
3. **最后磁盘**——`workspaces/<agent>/users/<旧名>/` → `users/<id>/`，同盘 `os.rename`；
4. 幂等可重试语义与 5.5 相同；存量幻影资源先跑 5.4 reclaim（按 id 改写）再执行本迁移。

### 8.5 对已落地批次的影响核查清单

| 批次 | 影响 |
|---|---|
| P0 | 无影响 |
| P1 3.1 `/me` | 返回体加 `name`；前端展示用 name、逻辑判断用 id/role |
| P1 3.2 白名单 | 校验对象改为登录名字段（regex 不变） |
| P2 `X-On-Behalf-Of` | 代操作头传 id；`common.py` 的用户清单与代操作参数改 id（name 仅作展示映射） |
| P3 5.1/5.2/5.4 | 清点/转移/reclaim 的记录类型扩展到 8.4-1 全量清单（**独立缺陷，无论是否拍板 ③ 都要修**） |
| P3.5 rename | 已实现的三存储 rename 保留为 8.4 迁移脚本内核；对外 rename API 降级为「改登录名」（只动 roles.json 的 name 键，不触发跨存储迁移、不触发 409） |
| P4 | design.md 增补：「user 以不可变 id 为主键，登录名 name 仅用于认证查找与展示」；回归矩阵加两条——① 改登录名后 id 不变，Redis owner/磁盘目录/会话全部不动；② 迁移脚本跑完后 `validate_setup.py` 全绿、全部存量用户可登录 |

### 8.6 本节拍板点

1. id 采用 base58 短串 10-12 位、admin 字面量豁免——确认或改 UUID；
2. 最小字段集（无 display_name）——确认；
3. **实施窗口**：迁库设计冻结前完成 8.4 迁移；若迁库排期提前，本轮 id 迁移与库表设计合并执行（roles.json 不落地 id 主键形态就等于白做）。

## 九、评审追加（2026-10-12）：用户表迁入 Redis——roles.json 降级为「引导种子 + 导出备份」（决策 ③ 的落库预演）

> 来源：继决策 ③（user 主键引入不可变 id）后的第三轮讨论。结论先行：
> **users / user_agents / admin_edit 整体迁入 Redis**——框架资源本就存 Redis，
> 不新增组件；roles.json 退为「首启引导种子 + 可导出备份」。建议与决策 ③
> 合并为一次迁移，roles.json 的键重构只做一遍。
>
> ✅ **实施状态（2026-10-12）**：本章方案已落地——`server/roles_store.py`
> （双实现 + 快照 + 冷备 + 补偿队列 + AOF 自检）、auth / role_access_policy /
> roles_admin_api 三消费方改造、`/roles/export` + `/roles/health` 端点、
> `scripts/migrate_users_to_redis.py`（dry-run + 顺序守卫 + 迁移后校验）、
> compose AOF 每秒落盘；落地形态摘记见 `docs/design.md` §13 Phase 7。
> P4 回归矩阵（9.9 末尾 8 条故障注入项）待执行。

### 9.1 为什么迁、为什么是现在

1. **消灭跨存储级联**：P3 删除生命周期、P3.5 rename 的复杂度根源是同一用户身份
   存两处（`roles.json` 文件 + Redis 资源 owner）。迁入后用户与资源同库，
   清点/转移/改名可在一次 Lua 脚本内原子完成；
2. **0.2 文件锁整体退役**：并发保护改 Redis 版本号 CAS，不再受单机文件锁限制，
   为未来多实例部署铺路；
3. **配置热更新提速**：5 秒轮询缓存（`auth.py:178-197` 与 role_access_policy.py
   同款）改为版本键比对，管理页保存秒级生效；
4. **不新增运维组件**：Redis 7 已在 `docker-compose.yml:4-12` 作为框架存储
   硬依赖运行，用户表迁入不引入新服务；
5. **对决策 ③ 是顺水推舟**：8.4 迁移本就要全量改写 `roles.json`（用户名→id），
   同一窗口把数据搬进 Redis，两轮改造一次落地。

> ✍️ 通俗解读：现在用户名单存在一个文本文件里，用户创建的资源存在 Redis
> 数据库里——「人」和「人的东西」分了家，删除、改名都要两边跑，还要加
> 文件锁防止两个管理员打架。把名单也搬进 Redis，人和东西放在一起，一次
> 操作搞定；而且 Redis 本来就在跑，不算新增的东西。

### 9.2 Redis 数据模型（沿用 8.2 的 id 口径）

```
roles:users        HASH   field=<id>    value=JSON{id, name, role, team, password}
roles:name         HASH   field=<name>  value=<id>      ← 登录索引（认证查这张）
roles:user_agents  HASH   field=<id>    value=JSON[<agent_id>, ...]
roles:config       HASH   admin_edit = "true"
roles:ver          STRING 自增整数                      ← 缓存失效标记
roles:pending_disk LIST   待重试磁盘操作 JSON{op, from, to}   ← 补偿队列（9.9）
```

- `admin` 沿 8.2 豁免：id 固定字面量 `"admin"`，索引里 `"admin" → "admin"`；
- `password` 为 `sha256$` 哈希原值，存进 value JSON——单一事实源，不留文件副本；
- 登录路径 = `HGET roles:name <输入名>` → id → `HGET roles:users <id>`，两跳 O(1)；
- rename = 改 value.name + `HSET roles:name 新名` + `HDEL roles:name 旧名`；
- 3.2 白名单校验对象不变（登录名 name）：写入口校验通过后落索引，重名先
  `HEXISTS` → 409。

> ✍️ 通俗解读：Redis 里用一张「用户总表」按 id 存每个人（名字、角色、密码
> 散列），另备一张「名字→id 对照表」专门给登录用。以后改名只动名字两个字段，
> id 和名下所有资源纹丝不动；重名在写入时就被拦下。

### 9.3 访问层收敛：新建 `server/roles_store.py`

- 接口与现 roles.json 读写同构：`load_all / save_all / upsert_user /
  delete_user / rename / resolve(name|id)->id`；同时提供 `FileRolesStore`
  文件实现作为回滚开关；
- 三个消费方只换数据源、业务逻辑零改动：
  1. `auth.py`——`load_users`（:146-163）、`load_roles_config`（:182-197）、
     `basic_auth_user`（:220-249）、`bootstrap_roles_file`（:118-143）改走 store；
  2. `role_access_policy.py`——5 秒轮询改为「每请求 `GET roles:ver`（一次轻量
     往返），版本变了才 `HGETALL` 重建本地缓存」；
  3. `roles_admin_api.py`——`GET/POST /roles` 对外契约不变（前端管理页零改动），
     `_roles_lock`（:83-123）、`_read_roles`/`_write_roles_unlocked`（:129-158）
     三个文件层函数整体退役。

> ✍️ 通俗解读：新写一个「用户数据中转站」模块，读用户、存用户都从它走。
> 认证、权限判断、管理接口三处只把「读文件」换成「问中转站」，判断逻辑
> 一行不改；管理页面照常工作，用户无感。

### 9.4 并发保护与原子性（替代 0.2 文件锁）

- 管理页「整表保存」语义不变，实现改 Redis 乐观锁：`WATCH roles:ver` → 读全量
  → 409 清点/密码哈希化等处理 → `MULTI` 写入 + `INCR roles:ver`；版本被他人
  抢先则返回 409「配置已被他人保存，请刷新后重试」；
- 5.1 清点 / 5.2 转移 / 5.5 rename 收敛为同库操作：转移可 Lua 原子完成，
  5.5/8.4 论证的「先 Redis 后 JSON」两阶段顺序约束自然消失；
- `X-On-Behalf-Of`、`/me` 等身份出口不变。

> ✍️ 通俗解读：原来靠锁文件防止两个管理员同时保存互相覆盖；现在改用
> Redis 的版本号——保存前看一眼版本号，保存时版本号变了就拒绝并提示
> 刷新。删除/改名/资源转移也因为在同一个库里，可以一口气做完，不会出现
> 做了一半的中间状态。

### 9.5 引导与迁移（幂等，顺序沿用 8.4 论证）

1. **首启导入**：Redis 无 `roles:users` 且 `config/roles.json` 存在 → 整体导入
   （若与决策 ③ 合并执行，此刻同步完成用户名→id 换键、Redis owner 改写、
   磁盘目录改名三件事，即 8.4 的全量清单）→ `roles.json` 改名
   `roles.json.imported-<时间戳>` 留档；脚本可重跑；
2. **空库引导**：Redis 空且无种子文件 → 生成 `admin` 引导账号
   （现 `bootstrap_roles_file` 逻辑平移进 store），`.env` 旧引导路径废弃；
3. **回滚**：新增 admin 端点 `GET /roles/export`——从 Redis 重建同构
   roles.json 落盘；运行开关切回 `FileRolesStore` 即整体回退文件模式，
   导出的 JSON 就是回滚包；
4. **持久化**：认证数据入 Redis 后丢库 = 全员无法登录——compose 的
   `redis:7-alpine` 须开启 AOF（`appendonly yes` + `appendfsync everysec`，
   官方镜像加 command 即可）；**启动自检**：`INFO persistence` 查
   `aof_enabled`，未开启则打 WARNING 横幅并拒绝用户写操作（防「忘配
   持久化」静默上线）；另每日定时走 export 同一条链路落 JSON 冷备
   （轮转保留 30 份，**即现成回滚包——回滚依赖冷备而非现场导出**，
   Redis 损坏时 export 接口本身不可用）。细化见 9.9。

> ✍️ 通俗解读：第一次启动时发现 Redis 里没有用户，就把老的名单文件整体
> 搬进去，老文件改名留档；搬过就跳过，重复跑不出错。想退回老方式，点一个
> 导出接口把 Redis 里的用户还原成文件即可。另外 Redis 要开「写日志」模式，
> 断电也不丢用户。

### 9.6 可用性降级（Redis 不可达时）

- store 进程内保留最后一份全量缓存：连接失败 → 进入**只读降级**——认证、
  鉴权、可见性继续用内存缓存（能登录、能干活），所有写操作返回 503
  「配置库暂不可用」；连接恢复自动回切；
- **快照落盘补强**：每次全量加载成功后同步写 `config/roles.snapshot.json`
  ——进程重启后内存缓存清空时，先读本地快照进入降级模式而非全员不可
  登录；连快照都没有的全新环境 fail closed，仅放行 bootstrap admin
  （快照与每日冷备复用同一条导出链路，几乎零增量成本）；
- **多实例明示**：降级窗口本就禁写（503），各实例缓存不一致仅剩「降级
  瞬间最后一写未广播」，窗口内权限视图可能滞后，恢复后按 `roles:ver`
  自动收敛——此为无法根除的残余风险，在此明示接受；
- 认证与资源读路径本就强依赖 Redis，降级策略保证抖动时系统退化为只读
  而非全站 500。风险全量清单与对策见 9.9。

> ✍️ 通俗解读：万一 Redis 抽风，系统不崩：大家还能正常登录使用（用的是
> 内存里留的最后一份名单），只是不能增删用户改配置，恢复后自动正常。

| P0 0.1 | 「JSON 损坏显式 500」语义平移为「Redis 异常显式 500/503」，静默吞错依旧禁止 |

### 9.8 本节拍板点

1. **切换范围**：users / user_agents / admin_edit 全量入 Redis，roles.json 只留
   引导 + 备份——确认；
2. **与决策 ③ 的执行顺序**：推荐**合并为一次迁移**（换 id 键 + 入 Redis 一步
   到位，roles.json 键重构只做一遍）；若拍板分开，必须 id 先行（8.4 完成后再
   迁 Redis），反序等于同批数据搬两遍；
3. **密码哈希随迁** Redis value（单一事实源）vs 留文件——推荐随迁；
4. **缓存失效机制**：版本键轮询（每请求 1 次 GET，无需订阅连接）vs
   pub/sub 推送——推荐版本键，简单且行为可预期；
5. **风险对策为工程硬约束**：9.9 对策表中「落点=代码内置」的各项（启动
   自检、每日冷备、快照落盘、补偿队列、HGETALL 使用约束、health 端点）
   随 `roles_store.py` 一次实现，不拆分期、不设可选开关。

> ✍️ 通俗解读：动手前确定四件事：① 用户名单全部搬进 Redis，原文件只当
> 「第一次开机的种子」和「备份」；② 换 id 和搬家合并成一次做完，省得数据
> 搬两遍；③ 密码散列跟着一起搬，不留两份；④ 改动何时生效用「版本号」判断
> ——版本号变了就重新加载，简单可靠。另有第五条：上一行的保险措施不是
> 可选项，是硬性要求，随 9.3 的中转站模块一次做完。

### 9.9 风险清单与对策（2026-10-12 第二轮评审：逐条闭环）

> 来源：对第九章方案的风险评审。结论：全部风险可收敛——多数以代码内置
> 机制消除，两项无法根除（跨存储缺口的失败窗口、降级瞬间的缓存滞后），
> 以「自动收敛 + 本节明示」处置。**「落点=代码内置」者为实现硬约束（见
> 9.8 拍板点 5），不作为可选项。**

| # | 风险 | 对策 | 落点 |
|---|------|------|------|
| 1 | AOF 忘配，Redis 重启用户表全丢（AOF everysec 本身也有 ≤1s 丢失窗口） | compose 写死 `--appendonly yes --appendfsync everysec`；启动自检 `INFO persistence` 的 `aof_enabled`，未开 → WARNING 横幅 + **拒绝全部用户写操作**（fail closed）；每日冷备兜底（见 #2） | 部署 + 代码内置 |
| 2 | 只靠 AOF，AOF 文件损坏 = 全部账号权限丢失；回滚时才导出，Redis 已坏则回滚包拿不出 | 定时冷备任务（绑应用生命周期，不依赖外部 cron）：每 24h 走 `export` 同一条链路落盘 `config/roles.backup-<date>.json`，轮转保留 30 份；**冷备文件即回滚包，禁止回滚时现场导出** | 代码内置 |
| 3 | 磁盘 `os.rename` 在 WATCH/MULTI 之外，「Redis 全部成功、磁盘失败」产生不一致 | 补偿队列 `roles:pending_disk`（9.2）：LPUSH 记账 → 执行 → 成功 LREM；后台每 5 min 幂等重试 + 启动对账；队列长度在 `/roles/health` 暴露，非 0 告警——从「人工救火」变「自动收敛」 | 代码内置 |
| 4 | 跨存储缺口本质无法消除（Lua 不能操作磁盘） | 磁盘操作全部幂等化：rename 前检查源/目标，目标已存在且内容一致 → 视为成功，重试永远安全；接受「窗口期存在、自动收敛」为明示残余风险 | 代码内置 + 本节明示 |
| 5 | `roles:users` 大 Hash big-key，HGETALL 阻塞单线程 | 约束固化在 store 内部：**业务鉴权路径只 HGET 单点查询；HGETALL 仅存在于首启导入与 export 两个方法**，注释禁止挪用；store 接口按单 id 查询设计，将来可换 per-user key 实现而调用方零改动 | 代码内置 |
| 6 | 多实例降级时各实例内存缓存版本不一致 | 写操作 `INCR roles:ver` 带版本 + 失效广播；降级窗口本就禁写（503），残余不一致仅剩「降级瞬间最后一写未广播」——明示「降级窗口内权限视图可能滞后、恢复后按 ver 自动收敛」 | 代码内置 + 本节明示 |
| 7 | 降级模式进程重启 → 内存快照清空，无人可登录 | **快照落盘**：每次全量加载成功后同步写 `config/roles.snapshot.json`；降级判定链 = Redis → 内存缓存 → 本地快照 → 连快照都没有时 fail closed（仅放行 bootstrap admin）；快照与冷备复用同一条导出链路 | 代码内置 |
| 8 | 迁移脚本四件事打包（id 换键 / Redis owner 改写 / 用户元数据入 Redis / 磁盘改名），链条长，bug 即账号权限错乱 | ① `--dry-run` 打印全部将执行的命令与 rename，零写入先演练；② 四步各自独立幂等、可单独执行；③ 迁移后自动校验（旧名残留=0、目录遗留=0、name↔id 双向一致）输出报告；④ 顺序守卫：检测到目标状态已部分完成或执行顺序颠倒直接拒绝 | 迁移脚本 |
| 9 | Redis 模式排查不直观（不能直接看文件） | `GET /roles/health`（连通性、AOF 开关、最后冷备时间、pending 队列长度）；`GET /roles/export` 保留；用户增删改写审计日志（谁、何时、改了什么） | 代码内置 |
| 10 | 账号权限 100% 强依赖 Redis，实例彻底损坏即全丢 | 恢复链三层：AOF（RPO ≤ 1s）→ 每日冷备（RPO ≤ 24h）→ 快照文件（RPO ≤ 进程生命周期）；冷路径（恢复）完全不依赖 Redis 存活 | 综合 #1/#2/#7 |

**启动自检序列**（app_factory 固定顺序）：
`PING → INFO persistence 查 AOF → 读 roles:pending_disk 队列长度 →
首启种子导入（9.5-1，仅当 roles:users 为空）→ 刷新快照落盘`。
任一步异常写横幅日志；AOF 未开启时拒绝用户写操作。

**P4 回归矩阵追加**（必须执行项，含故障注入场景）：

| # | 验证项 | 预期 |
|---|--------|------|
| 1 | 关闭 Redis AOF 后启动服务 | 弹出 WARNING 告警；新增/修改用户返回 503（fail closed） |
| 2 | Redis 重启（AOF 开启） | 用户数据无损，全员可登录 |
| 3 | 模拟磁盘目录操作失败（占位目标目录） | 任务进入 `roles:pending_disk` 补偿队列；后台定时自动重试成功后清除 |
| 4 | 模拟 Redis 网络断开（进程不重启） | 进入只读降级：登录鉴权正常可用，写操作返回 503 |
| 5 | Redis 不可达状态下重启应用进程 | 自动读取本地 `roles.snapshot.json` 快照进入降级模式，依然可登录 |
| 6 | 迁移脚本执行 `--dry-run` | 只打印完整执行清单，**不修改任何数据**（Redis/roles.json/磁盘零写入） |
| 7 | 制造迁移乱序条件（如 Redis 已含用户数据再跑导入） | 迁移脚本检测后**直接拒绝执行**并说明原因 |
| 8 | 杀掉进程模拟迁移中途崩溃，重启后观察 | 补偿队列继续完成未做完的磁盘任务，数据最终一致（旧名残留=0、目录遗留=0） |

> ✍️ 通俗解读：这一节把「搬家到 Redis」的所有风险列清楚并逐条上保险：
> 怕断电丢数据 → 开写日志 + 每天备份一份文件到磁盘；怕改到一半失败 →
> 失败的操作记在小本本（补偿队列）上自动重试；怕 Redis 挂了又赶上程序
> 重启没人能登录 → 磁盘上再留一份快照，重启先读快照；怕以后出问题查不了
> → 加一个「体检」接口看健康状态。真正无法 100% 消除的只有两处（Redis
> 挂掉瞬间的短暂不一致、磁盘操作失败的短暂窗口），都已设计成「自动恢复」
> 而不是「人工救火」。
